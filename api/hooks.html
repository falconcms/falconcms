Hooks API ​

Falcon CMS uses a WordPress-style hook system with Actions and Filters. There are 109 hooks total — 63 actions and 46 filters.

How It Works ​

Actions  → do_falcon_action()     → callbacks run, no return value
Filters  → apply_falcon_filters() → callbacks modify & return a value

The system is priority-based — multiple callbacks can attach to the same hook at different priorities (default: 10). Lower priority numbers run first.

Core Functions ​

php
// Register an action
add_falcon_action(string $tag, callable $callback, int $priority = 10): void

// Register a filter
add_falcon_filter(string $tag, callable $callback, int $priority = 10): void

// Fire an action (called internally by the CMS)
do_falcon_action(string $tag, ...$args): void

// Apply a filter chain (called internally, returns the filtered value)
apply_falcon_filters(string $tag, mixed $value, ...$args): mixed

// Check if a hook has registered callbacks
has_falcon_action(string $tag): bool
has_falcon_filter(string $tag): bool

// Remove a previously registered callback
remove_falcon_action(string $tag, callable $callback, int $priority = 10): void
remove_falcon_filter(string $tag, callable $callback, int $priority = 10): void

All hook registrations go in your theme's functions.php, a plugin's plugin.php, or a Laravel service provider. Themes and plugins load at the same point in the boot cycle, so every hook below is available to both.

Action Hooks ​

Admin Interface ​

falcon_admin_head ​

Fires inside the admin <head> tag. Use to inject custom CSS or meta tags.

php
add_falcon_action('falcon_admin_head', function() {
    echo '<link rel="stylesheet" href="/css/my-admin.css">';
    echo '<meta name="my-meta" content="value">';
});

falcon_admin_footer ​

Fires at the bottom of every admin page, before </body>. Use to inject JS or custom HTML.

php
add_falcon_action('falcon_admin_footer', function() {
    echo '<script src="/js/my-admin-script.js"></script>';
    echo '<p style="text-align:center;color:#999;">Built with ❤️ by My Company</p>';
});

falcon_admin_bar_right_before ​

Fires in the admin toolbar before the right-side content (notifications, user avatar).

php
add_falcon_action('falcon_admin_bar_right_before', function() {
    echo '<a href="/help" class="admin-bar-link">Help</a>';
});

falcon_settings_form_top ​

Fires at the top of the General Settings form. Add custom settings sections above the defaults.

php
add_falcon_action('falcon_settings_form_top', function() {
    echo '<div class="custom-settings-notice">Custom notice here</div>';
});

falcon_settings_form_bottom ​

Fires at the bottom of the General Settings form. Add custom settings sections below the defaults.

php
add_falcon_action('falcon_settings_form_bottom', function() {
    echo '<div class="my-plugin-settings">
        <h3>My Plugin Settings</h3>
        <input name="my_option" value="' . get_cms_option('my_option') . '">
    </div>';
});

falcon_seo_settings_form_top / falcon_seo_settings_form_bottom ​

Same pattern as general settings, but for the SEO settings page.

falcon_api_settings_form_bottom / falcon_integrations_settings_form_bottom / falcon_shop_settings_form_bottom ​

The same injection point on the REST API, Integrations and Shop settings forms. Anything echoed here renders inside that form and saves with it.

TIP

Instead of echoing raw markup, prefer falcon_add_settings_field() — it renders native rows, escapes values and handles saving on every one of these screens.

falcon_register_settings ​

Fires once, the first time settings fields are collected. The place to register fields and tabs for the settings screens.

php
add_falcon_action('falcon_register_settings', function () {
    falcon_add_settings_field([
        'id'     => 'my_api_key',
        'label'  => 'API Key',
        'type'   => 'text',
        'screen' => 'general',
    ]);
});

See the Settings Fields API.

falcon_admin_menu ​

Fires once, when the admin sidebar is first built. Register menu items and options pages here.

add_falcon_action('falcon_admin_menu', function () {
    falcon_add_menu_page([
        'slug'  => 'my-plugin',
        'title' => 'My Plugin',
        'icon'  => 'extension',

See the Admin Menu API.

falcon_login_form_after ​

Args: $where ('admin' or 'shop')

Fires inside the login card, under the sign-in form, on both login pages (modern and funny) with 'admin', and under the shop account page's sign-in with 'shop'. Echo another way to sign in — Falcon Security prints its "Sign in with a passkey" button (admin) and "Sign in with a code to your phone" (both) here. (Since v2.8.5; 'shop' since v2.8.6.)

php
add_falcon_action('falcon_login_form_after', function ($where) {
    if ($where !== 'admin') {
        return;
    }
    echo '<a href="/sso/start" class="btn-submit" style="display:block;text-align:center;margin-top:1rem">Sign in with SSO</a>';
});

falcon_header_actions ​

Fires inside the theme header's icon row (next to search and account). The shop plugin puts its cart icon here. Call it from a custom theme's header to get the cart icon.

falcon_after_footer ​

Fires after the footer, just before </body>. Use it for markup such as drawers and modals. The shop plugin adds its mini-cart here, or at falcon_footer if a theme has no falcon_after_footer.

E-commerce Logic Hooks ​

The hooks above change how the shop looks. These change what it does: prices, the cart, coupons, shipping, tax, checkout, payment, orders and stock. They are what a wholesale, role-pricing, B2B or multi-vendor plugin is built on.

Rules that apply to all of them:

  • No hook registered, no change. Every figure is exactly what it was without the hook.
  • What a filter returns is checked. A wrong type is ignored and the shop's own value is kept. A price below zero becomes 0. A sale price of 0 or less becomes "no sale".
  • Validation filters (*_validation, falcon_coupon_is_valid) take true. Return true to allow. Return a string to refuse: the string is the message the shopper sees.
  • Money is always recalculated on the server. No hook value is ever read from the browser.

Prices and catalogue ​

falcon_product_prices (filter) ​

Args: array $prices, int $postId, ?int $variationId, int $quantity, string $context

$prices is ['price' => float, 'sale_price' => float|null]. $context is 'display' (a page showing the price) or 'cart' (a cart line being priced; the order is written from it).

Every storefront price goes through this one filter: product cards, the single product page, the variable product's price range and its variation prices, the wishlist, the builder Product Meta element, the cart, and therefore the order. The page and the charge cannot disagree.

In the cart, $quantity is the line's quantity. The cart is re-priced every time it changes, so a tiered price follows the quantity.

php
// Wholesale: 20% off for the "wholesale" role, 30% off from 50 pieces.
add_falcon_filter('falcon_product_prices', function ($prices, $postId, $variationId, $quantity, $context) {
    if (!auth()->check() || auth()->user()->role?->slug !== 'wholesale') {
        return $prices;
    }
    $off = ($context === 'cart' && $quantity >= 50) ? 0.30 : 0.20;

    // Show the retail price struck through and the wholesale price as the "sale" price.
    return ['price' => $prices['price'], 'sale_price' => round($prices['price'] * (1 - $off), 2)];
});

Storefront templates read $product->shopData->current_price and current_sale_price, which go through this filter. price and active_sale_price stay the catalogue's own numbers (the admin edits those). In PHP, use falcon_product_prices($product, $variation = null, $quantity = 1).

Page cache: signed-in visitors never get a cached page, so prices that depend on the customer are safe. Do not change guest prices based on something only in the session. The cached page would show it to every guest.

Theme copies: a theme that copied the shop templates before this release still shows the catalogue price. The cart still charges the filtered price. Run php artisan shop:template to see which copies are behind (their @version is lower).

Hiding prices, and listing by a plugin's own prices ​

falcon_show_prices (filter) and falcon_hidden_price_html (filter) ​

Args: bool $show, $product / string $html, $product, string $context

Whether the visitor may see a product's price and buy it. falcon_can_see_prices($product) asks the first filter. It is always true unless a plugin says otherwise. When it is false:

  • product cards, the shop archive, the product pages, the wishlist and the builder's Product Meta element print falcon_hidden_price_html($product, 'price') in place of the price, and falcon_hidden_price_html($product, 'cart') in place of the buy button (a "See Detail" link when that is empty);
  • a variable product's variation prices are left out of the page source;
  • adding to the cart is refused (403). The message is the text of the 'cart' HTML;
  • the product's structured data leaves out offers, so search engines do not get the price.
php
// Prices for signed-in customers only.
add_falcon_filter('falcon_show_prices', fn ($show) => $show && auth()->check());
add_falcon_filter('falcon_hidden_price_html', fn ($html, $product, $context) => $context === 'cart'
    ? '<a href="/account" class="btn">Log in to buy</a>'
    : '<a href="/account">Log in to see prices</a>');

Guests share cached pages, so decide for all guests alike. Do not decide by something only in the session.

falcon_admin_product_data_tabs (filter) and falcon_admin_product_data_panels (action) ​

Args: array $tabs, ?Post $post / ?Post $post

Add a tab to the product editor's Product Data box. A tab is ['id' => 'my-tab', 'label' => 'My tab', 'icon' => 'storefront', 'show' => "productType !== 'variable'"]. icon is a Material Symbols name. show is optional: an Alpine expression that decides when the tab is visible. The id may use a-z 0-9 _ - and cannot be one of the built-in tabs.

Print the panel from the action as <div x-show="activeTab === 'my-tab'">…</div>. It is inside the product form and its Alpine scope (productType, variations…). Its fields are posted with the product, so save them in falcon_admin_after_save_product.

php
add_falcon_filter('falcon_admin_product_data_tabs', fn ($tabs) => [...$tabs, ['id' => 'supplier', 'label' => 'Supplier', 'icon' => 'local_shipping']]);
add_falcon_action('falcon_admin_product_data_panels', function ($post) {
    echo '<div x-show="activeTab === \'supplier\'"><input type="hidden" name="supplier_panel" value="1">'
       . '<input name="supplier_code" value="'.e(supplier_code($post)).'"></div>';
});
add_falcon_action('falcon_admin_after_save_product', function ($post, $shopData, $request) {
    if ($request->has('supplier_panel')) {
        save_supplier_code($post, $request->input('supplier_code'));
    }
});

Add a hidden marker field, as above, and save only when it is present. Then a save from a screen without your panel never clears your data.

falcon_admin_variation_fields (action) and falcon_admin_variation_meta (filter) ​

Args: ?Post $post / array $meta, array $input, ProductData $shopData

Variations are deleted and recreated every time a product is saved, so their ids change. Store per-variation data in the variation's own meta column (ProductVariation::$meta, an array), not in a table keyed by variation id.

The action prints once inside the editor's variation loop, where variation and vIndex are in scope. Bind your field to variation.meta.<your key> and name it 'variations['+vIndex+'][meta][<your key>]':

php
add_falcon_action('falcon_admin_variation_fields', function () {
    echo '<div class="md:col-span-2" x-init="variation.meta = variation.meta || {}">'
       . '<input x-model="variation.meta.supplier_code" :name="\'variations[\'+vIndex+\'][meta][supplier_code]\'">'
       . '</div>';
});

Both the Save button and the editor's "Save All Variations" button save it. The editor sends each variation's whole meta back on every save, so a key whose field is not on the page (for example because its plugin is turned off) is kept. Use the filter to check or clean what is stored. Return the array. An empty array is stored as null.
